* 준비: 최신 사용자 서보 전원 ON 확인. 새 서비스는 승인된 고정 춤 범위만 명시적 앱 시작으로 허용하며 USB/SPI/PipeWire 준비가 없으면 시작을 막는다. 전압 센서는 없으므로 5V·기구 공간은 매 시작 확인창에서 사용자가 확인한다. 일반 프로필의 verified/power_verified는 false 그대로다. 기존 GPIO 버튼은 옛 실행부에 남아 있고 새 BLE 대기 서비스에 아직 통합되지 않았다.
* 검사: 앱 로직 26개 통과, 실제 iPhone 개발 서명 빌드/설치 성공, Python 90개 중 86개 통과·기존 CAD 4개 건너뜀/문법 검사 성공. 저장 정보 재로드, 잘못된 토큰/다른 기기/권한 거부, 읽기만으로 lease 연장 금지, 정지 중 재인증 대기, 다른 인증 요청의 동작 응답 덮어쓰기 방지를 검사했다. 앱 개발 서명 만료는 **2026-10-13 01:05 KST**다. 실제 춤/Arduino 업로드/서보 명령/Git 작업은 이 배포에서 하지 않았다.
* 남은 검증: 외장 사운드카드는 사용자 확인상 분리 상태다. 재연결 후 USB 안정성/출력 장치 확인, 실제 무인터넷 조건의 춤·중단·링크 소실 시험, 새 실행부의 물리 종료 버튼 통합이 남아 있다. 로그와 자동 시작 설정 성공을 모든 실물 동작 검증 완료로 해석하지 않는다.

* USB 복구 확인: 사용자 재부팅 후 새 boot ID/SSH 접속, Arduino CH340 USB 인식 및 by-id→ttyUSB0 경로 복구를 확인했다. 사운드카드는 분리 상태, 서보 전원은 OFF다. 현재 부팅의 xHCI 장애 기록 없음, Arduino USB는 10초간 유지, `get_throttled=0x0` 확인. 옛 전시 autostart는 원본 보존/차단 상태이며 로봇 프로세스가 자동 시작하지 않았다. 별도 BLE 서비스만 **확인 인수 없이** 다시 준비해 idle/`motion_ready=false`로 춤을 잠갔다. Serial/PING/음성/서보 시험은 하지 않았다. 다음은 서보 전원 OFF 상태로 사운드카드 재연결 전후 USB·ALSA·드라이버 로그 비교다. 사운드카드가 장애 원인인지는 아직 미확정이다.

* USB 복구 준비: 사용자가 서보 전원 OFF 및 외장 USB 사운드카드 분리를 확인했다. 기존 `robot-demo.desktop`을 같은 autostart 폴더의 `.desktop.disabled-cuvo-usb-recovery-20261006` 접미사 파일로 옮겨 자동 실행을 차단했으며 원본 내용 SHA-256 일치를 확인했다. 춤 worker 없음/제어권 없음 확인 후 별도 BLE daemon을 정상 종료했다. **현재 BLE 서비스도 중지 상태**다. `sudo -n reboot`는 암호 필요, 표준 logind 재부팅도 대화형 인증 필요로 거부됐다. 따라서 아직 재부팅/USB 복구는 하지 못했고 사용자의 터미널 인증이 필요하다. 서보/Arduino/PWM 변경 없음. 옛 자동 실행을 임의로 복원하지 않는다.

* 외장 USB 사운드카드 후속 진단: 사용자가 새 사운드카드 연결을 알렸다. 커널 로그에서 `08bb:2902 / USB PnP Sound Device / C-Media Electronics Inc.` 인식 및 `snd-usb-audio` 등록을 확인했고 현재도 `snd_usb_audio` 모듈은 로드돼 있다. 연결 후 약 3576초 뒤 xHCI 장애로 사운드카드와 CH341 Arduino가 함께 해제됐다. 현재 ALSA에는 HDMI/내장 Headphones만 남아 있다. 드라이버 부재로 단정하지 않으며 사운드카드/USB 전원·접촉/커널 문제 중 실제 원인은 미확정이다. 다음 진단은 안전하게 USB를 복구한 뒤 사운드카드 제외/추가 전후 비교다. 드라이버 설치·제거/설정 변경/재부팅/소리 재생/서보 실행은 하지 않았다.

* USB 장애 후속 확인: 사용자는 Pi–Arduino 케이블이 연결돼 있다고 확인했다. Pi 커널에는 `xHCI host controller not responding, assume dead`, `HC died; cleaning up`과 CH341/USB 장치 연결 해제 기록이 있다. 현재 USB Serial 장치가 없고 `get_throttled=0x0`이다. 케이블 미연결이나 Arduino 고장으로 단정하지 않는다. USB 제어기 장애를 확인했지만 발생 원인은 미확정이다. 기존 사용자 autostart `robot-demo.desktop`은 활성 상태이므로 안전 조치 없이 재부팅하면 안 된다. 이 확인에서는 재부팅/USB 제어기 reset/Serial 열기/서보 실행/자동 실행 설정 변경을 하지 않았다.

* 최신 후속 보고: "로봇 응답이 늦어지고 있어요". 당시 Pi는 idle/제어권 유지/매초 요청 수신. 앱은 암호화 write 확인 뒤 전체 read도 수행하고 알림과 별도 해석한다. Pi는 성공한 claim의 요청 ID를 후속 read에 보존한다. 3초 안전 기준은 변경하지 않았다. 수정 앱 설치 및 별도 대기 BLE 서비스 갱신 후 사용자 "안 떠" 확인, Pi에서도 20초간 제어권 유지/revision 84→132 증가 확인. 앱 로직 20개/Python 83개 중 79개 통과·기존 CAD 4개 건너뜀/문법 검사 성공.
* 같은 후속 확인에서 춤 worker가 준비 단계 Serial 열기 `Errno 19 / No such device`로 실패했다. 읽기 전용 확인에서 by-id/ttyACM/ttyUSB 장치가 없고 lsusb에는 root hub만 있었다. **현재 error/준비 false/새 시작 잠금**이며 춤 성공이 아니다. 다음은 Arduino USB 연결 확인이다. 에이전트의 서보 시작/Arduino 작업/오류 초기화를 위한 자동 재시작/기존 전시·자동 실행·Git 작업은 없다.

* 후속 사용자 보고: 코드 입력 화면에 들어가기 전에 연결 확인이 취소된다. 실제 iPhone에서 상태 알림 구독 `CBATTErrorDomain(1): The handle is invalid.` 확인. 서비스/명령/상태 주소를 v1 고정값으로 바꾸고 Pi 대기 BLE 서비스만 갱신했다. 앱 서비스 무효화/1회 재탐색과 구독 전 초기 응답 보존도 추가했다. 사용자가 iPhone의 해당 기기를 지운 뒤 입력창 순간 진입 검사는 통과했지만, 사용자가 다시 입력창이 없다고 보고했다. 후속 시험에서는 BLE 연결은 유지되고 상태가 없는 것을 확인했다. 코드 제출 전에는 public 상태 read로 조회하고 제출 후에만 암호화 명령/heartbeat를 사용하도록 수정했다. 전체 read와 20바이트 알림을 분리해 처리하고 Pi Read Blob은 한 스냅샷을 유지한다. **최종 실제 iPhone 검색/선택/코드 입력창 15초 유지 검사 1개 통과**. 최종 개발 서명 수정 앱 빌드/설치/실행 완료. 인증 후 15초 유지 여부는 사용자 확인 대기다. 진단 시험은 코드를 입력하거나 서보를 시작하지 않았다.
* 최신 검사: 앱 로직 19개 통과, Python 82개 중 78개 통과/기존 CAD 4개 건너뜀. GATT 고정 주소/속성/UTF-8 분할, 전체 read·알림 교차와 Read Blob 동일 스냅샷 검사 포함. 이전 아래 검사 수보다 우선한다.
* 이후 사용자 코드 제출에서 `CBATTErrorDomain(15): Encryption is insufficient.` 확인. 명령 암호화 조건은 유지한다. Pi에 iPhone의 이전 bond가 남아 있어 사용자 명시 승인 후 **해당 iPhone 1건만** 제거했다. 다른 페어링 3건 보존, adapter Powered/Pairable 및 대기 BLE 재등록 확인. 새 코드 제출 후 사용자 "오 된것같은데??" 응답. Pi의 **새 Paired/Bonded/Connected, 제어권 true, 20초 동안 1초 간격 revision 증가**를 확인했다. 최종 확인도 idle/제어권 유지/준비 true다. 인증·지속 연결 성공이며 실제 춤/서보는 이 진단에서 실행하지 않았다.

## 2026-09-21 현장 확인 및 OLED 작업

이 절은 아래의 이전 개발 기록보다 최신이다. 아래 배포 대기 항목은 과거 시점의 기록이다.

* 같은 설정의 30초 관찰 시험 후 사용자가 3번도 실제로 표시된다고 확인했다. 최초 미관찰의 원인은 확정하지 않는다. SH1106 드라이버로 표시 가능함을 확인했으며 실제 칩명은 여전히 미확정이다.
