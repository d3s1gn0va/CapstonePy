# CUVO 로봇 동작 통합

## 최신 구현 안내 (2026-10-05)

최신 6축 기본값/범위와 새 양팔 교대 춤은 [20_DANCE_SESSION.md](20_DANCE_SESSION.md), 배포·검사 상태는 [09_CURRENT_STATE.md](09_CURRENT_STATE.md)를 우선한다. Mac 코드에는 상대 팔 각도 변환, 고개와 대각선 시선 전환, 새 음성 사용을 추가했다. 일반 그룹 명령은 6축 설정을 반영하고 과거 `TEST_*`는 거부한다. 통합 출력에도 실물 승인 배치 `swap=True`를 반영했다. 이후 Mega 실제 컴파일/업로드 검증, 별도 Pi 시험 폴더에서 사용자 확인 범위의 춤 1회(21.15초/오류 없음)를 완료했다. 정식 검증 플래그/기존 전시 코드/자동 실행은 유지하며 BLE 앱 연결은 미구현이다.

이하 문서는 초기 통합 및 과거 독립 시험 기록이다. 예전 고개 기본 45도, 팔 잠금/범위와 시험 명령을 현재 동작으로 사용하지 않는다. 기존 `main.py`는 이번에 변경하지 않았다.

최신 왼팔 Y축 독립 시험: 사용자 추정 범위 135..180 요청과 충돌 경고 후 재지시에 따라 `TEST_LEFT_Y_PAIR,<135_or_180>,CONFIRM_FROM_LAST_ZERO`를 추가했다. CH5만 직전 명령 0을 시작 가정으로 135(5000ms) -> 180(3000ms), 각 끝점 부팅당 한 번, 최종 유지. 일반 그룹 잠금/PWM 폭 유지, 실물 안전 범위 확정 아님. 검사/업로드 검증/PING/ACK·DONE 확인 완료. 다른 축은 업로드로 출력 해제됐으며 최신 상태는 `09_CURRENT_STATE.md`를 따른다.

최신 Y축 독립 시험: `TEST_ARM_Y_PAIR,<0_or_45>,CONFIRM_0_45_0`은 CH3/CH5에 0 -> 45 -> 0 순서를 부팅당 한 번만 허용한다. 최초 0 PWM 활성화 후 각 단계 3000ms, 최종 Y 출력 유지. 일반 그룹 잠금과 PWM 폭은 그대로이며 업로드로 이전 X 출력 유지가 해제됐다. 검사/업로드 검증/PING/각 ACK·DONE·최종 상태 확인 완료, 실물 움직임은 확인 필요. 상세 최신 상태는 `09_CURRENT_STATE.md`를 따른다.

최신 독립 시험: `TEST_ARM_X_HOLD,CONFIRM_FROM_ZERO`는 직전 0도 명령을 시작 가정으로 CH1 오른팔 X=0 / CH4 왼팔 X=180을 5초 동안 명령하고 유지한다. 확인 토큰/부팅당 한 번 제한, 일반 그룹 잠금과 PWM 설정 유지. 업로드 검증 및 ACK/DONE/상태 확인 완료; 실물 도달/안전 검증은 아니다. 상세 최신 상태는 `09_CURRENT_STATE.md`를 따른다.

2026-10-05. 사용자 범위는 **로봇 동작 통합만**이다. 휴대폰 앱, 카메라 촬영/인식/저장은 이번 구현에 포함하지 않는다. 사용자는 이전 채널표대로 배선했다고 확인했다. 새 팔의 안전 각도와 초기 자세를 확인했다는 뜻은 아니다.

최신 결과: 사용자 기구 관찰로 고개/정수리 기본 45도(범위 0..90), 오른팔 X 기본 180도/감소 방향을 기록했다. 새 펌웨어 업로드/검증 후 CH0=45, CH1=180, CH2=45 순차 ACK/DONE 및 ENABLED/IDLE을 확인했다. CH3/4/5는 움직이지 않았고 업로드 후 출력 비활성이다. 안전 범위 전체와 실물 기본 자세의 확인은 별개다. 사용자 지시 "앞으로 그냥 바로 너가 업로드 해"에 따라 요청한 변경에 필요한 업로드에는 재승인을 묻지 않지만 검사/중지/포트/검증/PING 절차를 유지한다.

## 구현 계획과 현재 단계

**실물 결과 정정:** 사용자는 최신 세 축 기본 자세 시험에서 "아무것도 안움직였어"라고 보고했다. ACK/DONE과 ENABLED/IDLE은 펌웨어 상태일 뿐 실제 이동 확인이 아니다. 추가 실행 없이 외부 서보 전원과 배선 점검을 먼저 진행한다. 아래 구현/통신 성공을 기구 동작 성공과 혼동하지 않는다.

1. 완료: 기존 `main.py` 기본 동작을 보존하고 별도 통합 실행부를 추가했다.
2. 완료: 눈, 두 WAV, 고개/팔, 정수리와 LED를 단일 실행 흐름에서 관리한다.
3. 완료: Arduino 소스에 그룹 이동과 6채널 중단/출력 해제를 추가했다. 미확정 팔은 그룹 이동에서 잠갔다.
4. 완료: Python 문법, 가상 동작/오류, 가짜 Serial/PWM 검사를 수행했다. 초기 구현은 컴파일만 했고 이후 명시적인 승인으로 아래 90도 시험용 펌웨어를 업로드했다.
5. 대기: 전원 검증, 팔 4축의 초기/안전/몸짓 각도 캘리브레이션, Pi와 Arduino 설정 일치.
6. 대기: 사용자 지시와 준비 완료 후 Pi 통합 배포, 보정값을 반영한 후속 펌웨어 업로드/검증, 요청된 실물 통합 시험, 자동 실행 전환. 업로드 재승인 대신 최신 위임과 `AGENTS.md` 절차를 따른다.

기구물 완성과 소프트웨어 배포/검증 완료는 구분한다. **최신 기본 자세 시험은 기존 Pi 전시 프로그램을 중지한 상태로 CH0/1/2만 실행했다.** 독립 시험 파일은 `~/capstone-robot-build/home_pose_test/`에 복사했으며 Pi 통합 코드는 전체 미배포다. 나머지 팔 축/몸짓/전원 검증은 미완료다. [현재 상태](09_CURRENT_STATE.md)를 우선 읽는다.

## 배선과 설정

팔 좌우는 로봇 기준이다. 눈 좌우는 정면 관찰자 기준이다.

| 채널 | 역할 | 통합 초기 각도 | 통합 안전 범위 |
| --- | --- | --- | --- |
| CH0 | 고개 | 45도(정면) | 사용자 요청 0..90도 |
| CH1 | 오른쪽 어깨 X | 180도(내린 자세 목표) | 잠정 135..180도, 전체 기구 검증 필요 |
| CH2 | 카메라가 달린 정수리 | 45도(정면) | 사용자 요청 0..90도 |
| CH3 | 오른쪽 어깨 Y | 미확정 | 미확정 |
| CH4 | 왼쪽 어깨 X | 미확정 | 미확정 |
| CH5 | 왼쪽 어깨 Y | 미확정 | 미확정 |

사용자는 오른팔 X의 0도 명령이 번쩍 올린 상태이고 기본은 180도라고 설명했다. 나머지 팔 축의 물리 방향/기본값은 확인 필요다. 모든 축의 `verified`와 `power_verified`는 여전히 `false`다. 몸짓은 `greeting`과 `invitation`에서 따로 지정하며 팔 목표는 아직 `null`이다.

### 오른팔 상대 자세와 서보 명령 분리

사용자는 내린 자세를 상대 0도로 정했고, 최신 관찰로 오른팔 X의 실제 기본을 180도로 지정했다. 왼팔과 반대 방향 요청에 따라 X는 `servo_zero=180`, `direction=-1`로 기록했다. 왼팔 자체의 기본값/방향은 아직 확인 필요다. Y는 상대 0..45도 요청이며 사용자가 말한 옆으로 들어 올리는 축이다.

`MotionProfile.servo_angle()`은 `servo_zero + direction * 상대 각도`로 변환한다. X는 상대 0 -> 실제 180, +45 -> 135다. 이전 -45..45 요청 중 -45는 실제 225가 되어 불가능하므로 현재 유효 상대 범위는 0..45, 실제 범위는 135..180으로 제한했다. 상대 음수와 기존 0..180 전체 범위는 자동 허용하지 않는다. 전체 기구 범위를 실제 검증했다는 뜻은 아니다. Y의 기준/방향은 여전히 `null`이다. 각도를 잘라서 변환하는 보정은 하지 않는다.

`targets()`와 Serial은 실제 서보 숫자만 사용한다. X의 기본 180은 기록했지만 다른 팔 기본값/몸짓은 `null`이어서 통합 실물 실행은 잠긴다. 기존 Pi 전시 코드 90->180->90은 새 오른팔 범위와 맞지 않는다. 기존 `main.py`는 중지 상태를 유지하며 재부팅/재시작하지 않는다.

실물 실행에는 6축 모두의 안전 최소/최대, 초기 각도, 실제 기구 확인과 전원 확인, 몸짓 목표가 필요하다. 누락이 있으면 GPIO나 USB Serial을 열기 전에 거부한다. 시험 파일에서 사용하는 85..95도/90도 값은 **단위 검사 전용 가짜 값**이며 실제 로봇의 설정이 아니다.

Arduino의 `GROUP_SAFE_MIN_DEG`, `GROUP_SAFE_MAX_DEG`, `GROUP_NEUTRAL_DEG`도 같은 값으로 설정한다. CH3/4/5의 `-1`은 미설정 표시다. `CAPS`로 읽은 여섯 채널의 범위/초기 값이 Pi 프로필과 정확히 같아야 실행한다.

OLED는 기존 승인된 CAD + 바깥쪽 3픽셀, 10픽셀 선, 밝기 255, 좌우 28픽셀 및 복귀 깜박임을 유지한다. 새 CE1 배선 기준은 DC 물리 7번 / RST 12번 / GND 9번이다. Pi의 별도 OLED 시험 폴더에는 아직 이전 DC/RST 설정이 남아 있음을 읽기 전용으로 확인했다. 재배선과 코드 반영을 함께 확인해야 한다.

## 통합 동작

통합 프로그램의 시연:

1. 정면 왼쪽 시선 이동, 정면 복귀와 깜박임.
2. 고개와 오른쪽 어깨 두 축의 인사 자세 이동(1200ms), 첫 WAV를 함께 시작.
3. 이동 완료 응답과 음성 종료를 모두 확인하고 기존 간격 0.15 + 0.25초 대기.
4. 왼쪽 어깨 두 축의 초대 자세 이동(1200ms), 두 번째 WAV를 함께 시작.
5. 둘 다 완료한 뒤 0.5초 유지.
6. 고개와 양팔 네 축을 초기 자세로 함께 복귀(1800ms), 완료 응답 확인.
7. 정면 깜박임 후 대기.

가상 실행은 현재 WAV 길이 기준 약 9.4초였다. 실제 완료 응답/통신 지연을 포함한 실물 측정값이 아니다. 이전 문서의 약 15초 시나리오는 제안안이며 이번 기본 통합 흐름과 구분한다. 최종 전시 연출과 팔 몸짓은 실물 확인 후 조정한다.

Mac 통합 카메라 동작은 CH2 프로필의 최소 -> 최대 -> 기본, 현재 0 -> 90 -> 45도로 이동하며 2000/2000/1500ms를 유지한다. 실제 이번 시험에서 이 스윕은 실행하지 않았다. 이 동안 LED를 켜고 종료/중단/오류 시 끈다. Pi 기존 코드에는 아직 30/150/90이 남아 있어 재시작하지 않는다.

하드웨어 모드는 PING, 펌웨어 설정 일치와 자원 소유를 확인한 뒤 6축 초기 자세를 설정하고 세 버튼을 기다린다. OLED는 대기 중에도 깜박인다. 시작 시 눌려 있는 버튼과 동작 중 추가 입력은 나중에 실행할 명령으로 쌓지 않는다.

## 중단과 안전

* 실행 흐름 하나가 Serial과 OLED를 소유한다. 기존 프로그램이나 단독 OLED 시험과 함께 실행하지 않는다. `fuser`로 Serial 사용 여부를 확인하고 확인할 수 없으면 거부한다.
* 이동 응답을 타이머만으로 완료로 취급하지 않는다. DONE 누락, 음성 실패, OLED 실패는 오류로 전환하고 가능한 경우 STOP을 보낸다.
* SIGINT/SIGTERM 중단은 STOP과 음성 종료를 요청한다. 자동 복귀나 DISABLE은 하지 않는다. STOP은 PWM 유지이며 기계식 비상 정지/전체 전원 차단이 아니다.
* STOP 응답을 확인하지 못하면 정지 완료가 아닌 오류로 표시한다. 오류 후 자동으로 시연을 재개하지 않는다.
* 안전 종료 버튼은 이동/음성을 중단한 뒤 Pi OS 종료를 요청한다. 전체 전원은 별도로 끈다. 권한/중단 오류를 성공으로 표시하지 않는다.
* ACK/STOP 통신과 오디오 정리는 유한 대기 시간이 있으며 실시간 안전 보장을 제공하지 않는다. 전시자가 접근할 수 있는 서보 전원 차단 수단이 필요하다.
* 첫 PWM 활성화에는 실제 각도 피드백이 없어서 이동 속도를 보장할 수 없다. 그룹 명령은 출력이 꺼진 축에 초기 각도만 첫 목표로 허용하지만 물리적 급이동을 제거하는 기능은 아니다. 서보혼/기구를 안전하게 정렬하고 초기 자세를 개별 확인한다.
* PWM 50Hz / 1000..2000us는 변경하지 않았다. 최신 레거시 이동 명령의 범위도 고개/정수리 0..90, 오른팔 X 135..180으로 갱신했다. `CENTER`와 고정 0/90 시험은 별도 명시적 캘리브레이션용이며 일반 전시 기본 자세가 아니다.
* 기존 `main.py`는 중지 상태다. 새 팔 기구의 미확정 각도를 검증하지 않고 이전 기본/목표가 남아 있어 재시작하지 않는다.

## Serial 확장

```text
CAPS
CAPS,MOVE_GROUP,0:0:90:45,1:135:180:180,2:0:90:45,3:-1:-1:-1,4:-1:-1:-1,5:-1:-1:-1

MOVE_GROUP,<duration_ms>,<channel>,<angle>[,<channel>,<angle>...]
ACK,MOVE_GROUP
DONE,MOVE_GROUP
```

위 채널 쌍은 `채널:최소:최대:초기`다. 기간은 1..60000ms, 채널은 0..5 중 중복 없는 1..6개다. 명령의 모든 대상과 안전 범위를 검증한 뒤에만 출력한다. 공유 시작 시각과 동일 기간으로 이동한다. I2C 출력은 순차적이고 서보의 물리 도달 시각까지 같다는 뜻은 아니다.

기존 `MOVE_HEAD`, `MOVE_ARM`, `MOVE_CAMERA`, `MOVE_BOTH`, `CENTER`와 `STATUS`는 유지했다. `STATUS`는 기존 3축 형식이고 `CAPS`는 새 그룹의 6축 설정이다. STOP/DISABLE은 새 코드에서 여섯 채널 모두에 적용된다. 기존 펌웨어는 새 CAPS/GROUP 명령을 지원하지 않으므로 그대로는 통합 실행할 수 없다.

### 기본 자세 전용 시험 (최신)

양팔 X축 고정 시험: `TEST_ARM_X_PAIR_CAPS` -> `CAPS,TEST_ARM_X_PAIR,1:4,180_THEN_0,ONCE_PER_BOOT`. `TEST_ARM_X_PAIR,<angle>,<duration_ms>,CONFIRM_ENDPOINTS`는 CH1/CH4만 동일 명령값 180 -> 0 순서로 공통 시작 시각에 움직이며 각 단계 ACK/DONE을 반환한다. 각도는 0/180만, 기간은 5000..10000ms, 부팅당 끝점별 한 번이며 0은 두 축의 소프트웨어 180 완료 후에만 허용한다. 생산용 프로필이나 미확정 왼팔 그룹 범위를 해제하지 않는다. 최초 PWM 저장 각도는 실제 위치 피드백이 아니고 전체 기구 범위는 미검증이다. 원격 재접속/리셋을 이용한 자동 반복은 하지 않는다. [최신 시험 결과](09_CURRENT_STATE.md)를 따른다.

추가 고정 시험: `TEST_RIGHT_Y_CAPS`는 `CAPS,TEST_RIGHT_Y_45,3:45,ONCE_PER_BOOT`를 반환한다. `TEST_RIGHT_Y_45,CONFIRM_45`는 CH3에 45도 PWM만 설정하고 ACK/DONE을 반환하며 부팅당 한 번이다. 시작 각도/이동 시간을 추정하지 않으므로 최초 활성화 때 급이동할 수 있고, DONE은 물리 도달 확인이 아니다. CH3의 일반 그룹 잠금/프로필 미확정 상태는 유지한다. 실제 업로드/명령 완료 결과와 사용자 실물 확인 여부는 [최신 상태](09_CURRENT_STATE.md)를 따른다.

`test_home_pose.py --confirm-home-pose-from-0`는 PING/지원 확인 후 CH0=45(5000ms), CH1=180(10000ms), CH2=45(5000ms)만 순차 명령하며 ACK/DONE/최종 상태를 확인한다. `TEST_HOME_POSE,<channel>,<duration_ms>,CONFIRM_FROM_0`는 CH0..2의 고정 목표만 허용하고 신규 비활성 채널/부팅당 한 번을 요구한다. 시작 0은 직전 사용자 시험 상태 가정이며 센서 값이 아니다. 임의 재부팅이나 자동 반복으로 재실행 조건을 만들지 않는다.

업로드/Serial 초기화 후 CH3/4/5는 출력 비활성이다. `STATUS_GROUP`의 이 축 90 표시는 부팅 소프트웨어 추정값이지 실제 이동 명령/물리 측정이 아니다. 오류는 STOP을 시도하고 자동 복귀/전시 재시작 없이 중단한다. 성공 후 CH0/1/2의 PWM만 유지한다.

### 사용자 승인에 따른 90도 고정 시험 (이전)

```text
TEST_CENTER_CAPS
CAPS,TEST_CENTER_90,90,ONCE_PER_CHANNEL
TEST_CENTER_90,<channel>,<duration_ms>,CONFIRM_90
ACK,TEST_CENTER_90,<channel>,90
DONE,TEST_CENTER_90,<channel>,90
STATUS_GROUP
```

채널 0..5, 기간 1000..10000ms이며 부팅당 채널별 한 번만 허용한다. 임의 각도나 범위 변경은 지원하지 않는다. 그룹의 팔 잠금과 프로필 초기 값은 바꾸지 않는다. 이 기능은 실물 안전 확인을 대신하는 기능이 아니라 사용자가 위험 안내 후 명시적으로 요청한 캘리브레이션 전 시험이다. Serial 토큰은 사용자 승인 절차를 대신하지 않는다.

2026-10-05 실제 업로드(`--verify`)와 순차 90도 시험을 성공했다. 각 채널 3000ms/채널 간 0.5초, 마지막 6축 상태는 90도/출력 켜짐/이동 종료였다. 첫 PWM은 실제 위치 피드백이 없어 급이동할 수 있고 DONE은 물리 도달의 센서 확인이 아니다. PWM 출력은 유지하고 기존 프로그램은 중지했다. 전시·카메라·전원 OFF 버튼은 비활성이다. 기존 자동 실행 등록은 아직 남아 있으므로 다음 부팅 때 예전 프로그램이 실행될 수 있다. 재시작이나 재시험은 자동 진행하지 않는다.

현재 Pi의 독립 시험 위치는 `~/capstone-robot-build/center_90_test/test_servo_center_90.py`다. 기본 실행은 거부하고 `--confirm-physical-90`가 필요하며 이후 실행 역시 새 사용자 지시와 현장 안전 판단이 필요하다. 부팅당 한 번 제한을 피하기 위한 자동 리셋은 하지 않는다. 시험 각도를 기본값 또는 안전 범위로 저장하지 않는다.

### 0도 고정 시험 준비

```text
TEST_ZERO_CAPS
CAPS,TEST_ZERO_0,0,ONCE_PER_CHANNEL
TEST_ZERO_0,<channel>,<duration_ms>,CONFIRM_0
ACK,TEST_ZERO_0,<channel>,0
DONE,TEST_ZERO_0,<channel>,0
```

사용자는 예전 기구의 각도 제한으로 현재 0도 시험을 막지 말라고 요청했다. 전시용 범위와 독립적인 고정 0도 시험을 추가했고 채널별 부팅당 한 번/명시적 확인/동작 중 새 명령 거부를 유지한다. 임의 각도 이동이나 자동 실행을 풀지 않는다. 현재 오른팔/정수리 레거시 제한의 정확성도 확정하지 않는다.

`test_servo_zero_0.py --confirm-physical-0`는 CH0~CH5를 한 개씩 5000ms/완료 후 0.5초 간격으로 실행하는 별도 시험 진입점이다. 명령 0도는 기존 PWM 변환의 1000us에 해당하며 새로운 펄스 폭 설정이 아니다. 실제 0도/내린 자세/안전 범위 검증은 별개다. 첫 출력 때 실제 위치 피드백이 없으므로 90도 추정값 활성화가 급이동을 만들 수 있다.

검사 53개 중 49개 통과/기존 CAD 4개 건너뜀, 가짜 PWM 검사와 Mega 컴파일 통과: Flash 15462바이트(6%), SRAM 2632바이트(32%). 사용자 승인 후 `zero_0_test/binaries/`에서 실제 Mega 업로드/검증을 완료했다. 공유 실행부와 0도 진입점은 `~/capstone-robot-build/zero_0_test/`에 복사하여 6채널 순차 시험을 종료 코드 0으로 완료했다. 마지막 상태는 `STATUS_GROUP,0:0:ENABLED:IDLE,1:0:ENABLED:IDLE,2:0:ENABLED:IDLE,3:0:ENABLED:IDLE,4:0:ENABLED:IDLE,5:0:ENABLED:IDLE`였다. 명령 완료 확인이며 물리 각도 피드백은 아니다. 기본값/전시 프로그램/자동 실행은 바꾸지 않았다.

## 검사와 실행

Mac에서 실제 하드웨어를 사용하지 않는 확인:

```bash
bash scripts/check_python.sh
python3 -B raspberry_pi/robot_demo/integrated_demo.py --simulate
python3 -B raspberry_pi/robot_demo/integrated_demo.py --simulate --action camera
python3 -B -m unittest discover -s tests -p 'test_integration.py' -v

c++ -std=c++17 -Wall -Wextra -I tests/firmware_stubs tests/firmware_group_test.cpp -o /tmp/cuvo-firmware-group-test
/tmp/cuvo-firmware-group-test
```

Pillow가 있는 개발 Python으로 전체 검사도 실행했다. 42개 중 38개 통과, `ezdxf`가 필요한 기존 CAD 변환 4개는 건너뛰었다. CAD/마스크 원본은 변경하지 않았다.

초기 원격 컴파일 결과: FQBN `arduino:avr:mega`, Arduino CLI 1.5.1, AVR 1.8.8, Adafruit PWM 3.0.3/BusIO 1.17.4. Flash 14192바이트(5%), SRAM 2143바이트(26%)였다. 이후 90도 시험 명령 추가 버전은 Flash 15104바이트(5%), SRAM 2500바이트(30%)로 컴파일해 승인 후 업로드/검증했다. 최신 Python 검사는 49개 중 45개 통과/기존 CAD 4개 건너뜀이다. 실제 통합 전시 실행 검증은 아니다.

실제 Pi의 시스템 Python에는 `serial`/`gpiozero`/Pillow가 있지만 `luma`는 없다. 기존 OLED 시험 가상환경은 시스템 패키지를 공유하며 네 패키지가 모두 있음을 읽기 전용으로 확인했다. 새 패키지를 설치하지 않았다. 향후 시작 스크립트도 모든 의존성이 있는 Python을 사용하도록 설정해야 한다.

준비 완료 후, Pi에 통합 파일을 배포했다면 기존 OLED 가상환경을 이용하는 실물 진입점은 다음과 같다. **지금은 실행하지 않는다.**

```bash
~/cuvo_oled_test/.venv/bin/python ~/robot_demo/integrated_demo.py --hardware
```

프로필/기구/전원을 확인하고 기존 프로그램을 중지한 뒤, 사용자 요청 범위에서 배포·필요한 펌웨어 업로드/검증·실물 시험·자동 실행 전환을 구분해 진행한다. 업로드는 최신 위임에 따라 재승인 없이 가능하지만 요청하지 않은 시험/자동 실행은 하지 않는다. 기존 시작 스크립트는 아직 시스템 Python의 `main.py`를 가리킨다.
